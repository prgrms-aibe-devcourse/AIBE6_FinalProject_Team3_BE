# 임장 체크리스트(checklist) 도메인 — 구현 현황 정리

## 배경 / 성격

다른 문서(`auth-design.md`, `user-design.md`, `property-design.md`, `market-data-design.md`)와 같은 방식의 **회고성(retroactive) 문서**입니다. 다만 이 도메인은 다른 팀원의 코드가 아니라 **이 프로젝트에서 TDD로 직접 구현한 도메인**입니다 — 처음 구현할 당시엔 이 공식 요구사항 명세서가 아니라 내부 브레인스토밍 결과(`docs/superpowers/specs/2026-07-23-checklist-design.md`)를 기반으로 진행했기 때문에, 이번에 처음 받은 공식 명세서와 대조해 차이를 확인하는 성격입니다. 그래서 "왜 이렇게 구현했는지"는 대부분 알고 있지만, 명세서와 다른 부분은 동일하게 표시했습니다.

**범위**: `com.algogyeyak.checklist.*`(체크리스트 생성/조회/항목 확인/결과 확인)만 다룹니다.

## 주요 Entity — 요구사항 대비 실제

| Entity | 요구사항 | 실제 |
|---|---|---|
| `Checklist` | id, userId, propertyId, templateVersion, status | 동일 (연관관계는 `Long` FK가 아니라 `User`/`Property` 실제 엔티티 참조) |
| `ChecklistItem` | id, checklistId, category, content, importance, checked, issueFound | 필드가 더 많음 — `guideText`(안내 문구), `itemType`(CHECK/YES_NO/DATE/DOCUMENT_REQUEST), `code`(자동판정용 식별자), `value`(Y/N·날짜·서류제공여부 응답값), `userNote`(미흡 메모) 추가. 요구사항 본문의 "Y/N 또는 날짜 입력", "제공됨/미제공 반영" 요구를 담기 위해 필요했던 확장으로 보임 |

## 체크리스트 문항 구성 — 요구사항 대비

시드 데이터(`ChecklistTemplateSeedData`, 버전 1) 기준 **총 23개, 5개 카테고리**로 요구사항의 "20~24개" 범위 안에 들고, 카테고리별 개수도 요구사항 범위와 일치합니다.

| 카테고리 | 요구사항 개수 | 실제 개수 |
|---|---|---|
| 실내 상태 | 4~5개 | 5개 ✅ |
| 소음·환경 | 2~3개 | 3개 ✅ |
| 보안·안전 | 3~4개 | 4개 ✅ |
| 서류·행정 | 8개 | 8개 ✅ |
| 주변 환경 | 2~3개 | 3개 ✅ |

서류·행정 8개 항목(등기부등본 확인, 신탁등기 여부, 명의 일치, 소유권 취득일, 세금체납 안내, 확정일자 부여현황 요청, 전입세대열람원 요청, 계약조건 재확인) 모두 요구사항과 1:1로 대응됩니다.

⚠️ **명의 일치 항목 문구 방향이 반대입니다.** 요구사항은 "명의 불일치(Y) 응답 시 자동 issueFound"라고 되어 있는데, 실제 문항은 **"소유자와 임대인의 명의가 일치하나요?"**로 물어서 **"N"(불일치)일 때 issueFound**가 됩니다. 동작 자체(불일치하면 주의 항목)는 요구사항과 같지만, Y/N 방향이 반대라 요구사항 문서만 보고 API를 연동하면 혼동될 수 있습니다.

⚠️ **매물유형·거래유형별 문항 분기가 없습니다.** 요구사항은 "매물유형·거래유형을 확인하고... 생성"이라고 되어 있어 유형별로 다른 문항 세트를 암시하지만, 실제로는 **버전 1 템플릿 하나만 존재하고 모든 매물에 동일하게 적용**됩니다(소스 주석에도 "매물유형·거래유형별 분기는 아직 두지 않는다"고 명시). 유형별 분기가 필요한 요구사항인지, 향후 과제인지 확인이 필요합니다.

## 체크리스트 생성 (`POST /properties/{propertyId}/checklists`) — 요구사항 대비

| 요구사항 | 실제 구현 |
|---|---|
| 매물 접근 권한 확인 | ✅ (매물 존재 + 소유자 확인) |
| 매물유형·거래유형에 맞는 템플릿으로 생성 | 위 참고 — 실제로는 유형 무관 공통 템플릿 |
| 기존 체크리스트 있으면 재생성하지 않고 그대로 반환 | ✅ `createOrGetChecklist` (멱등), DB에도 `(user_id, property_id)` 유니크 제약으로 이중 보장 |
| 실패: 존재하지 않는 매물 | ✅ 404 |
| 실패: 접근 권한 없음 | ✅ 403 |
| 실패: 매물 정보 부족 | ❌ **관련 검증 로직 자체가 없음** — 전용 에러코드도 없어 이 실패 케이스는 발생하지 않음 |
| 실패: 지원하지 않는 매물 유형 | ❌ **관련 검증 로직 자체가 없음** — 유형 분기가 없으니 "지원하지 않는 유형"이라는 개념 자체가 없음 |

## 체크리스트 조회 (`GET /properties/{propertyId}/checklists`) — 요구사항 대비

| 요구사항 | 실제 구현 |
|---|---|
| 접근 권한 확인 | ✅ (구현 자체는 소유자 확인 로직이 있음 — 단, `getChecklist`는 현재 `updateChecklistItem`/`getChecklistResult`처럼 `checklist.getUser().getId().equals(userId)`를 직접 비교하지 않고 `findByUserIdAndPropertyId(userId, propertyId)`로 쿼리 자체에 userId 조건을 걸어 접근 제어를 함 — 결과적으로 동일한 효과) |
| 카테고리·중요도 순 정렬 | ⚠️ **명시적 정렬 로직이 없습니다.** 문항은 생성 시 저장된 `displayOrder` 그대로 반환됩니다. 시드 데이터가 카테고리별로 순차 등록돼 있어 카테고리끼리는 우연히 묶여 보이지만, **카테고리 내 중요도(REQUIRED/GENERAL) 순 정렬은 전혀 반영되지 않습니다** |
| 확인/주의 항목 구분 | ✅ 응답 항목마다 `checked`, `issueFound` 필드로 구분 제공 |
| 실패: 존재하지 않는 체크리스트 | ✅ 404 |
| 실패: 접근 권한 없음 | 위 참고 — 소유자가 아니면 그냥 404로 처리됨(별도 403 없음). 매물/체크리스트 수정·삭제 API들이 403/404를 구분하는 것과는 다른 패턴 |
| 실패: 삭제된 매물에 연결된 체크리스트 | ❌ **검증 로직이 없습니다.** 매물이 나중에 삭제돼도 이미 만들어진 체크리스트는 계속 조회 가능 |

## 체크리스트 항목 확인 (`PATCH /checklists/{checklistId}/items/{itemId}`) — 요구사항 대비

| 요구사항 | 실제 구현 |
|---|---|
| 접근 권한 확인 | ✅ 403 (`checklist.getUser().getId().equals(userId)`) |
| 체크 상태(또는 Y/N·날짜값) 저장 | ✅ `check()`/`answer()`로 분기 처리 |
| 서류 미제공 시 자동 issueFound | ✅ `DOCUMENT_REQUEST` 타입에서 `NOT_PROVIDED` 응답 시 자동 반영 |
| 신탁등기 있음(Y)/명의 불일치 자동 issueFound | ✅ (명의 쪽은 위에서 언급한 Y/N 방향 차이 있음) |
| 확인한 항목 수·주의 항목 수 갱신 | ✅ `refreshStatus()`가 매 변경마다 호출됨 |
| 실패: 존재하지 않는 체크리스트 항목 | ✅ 404 |
| 실패: 접근 권한 없음 | ✅ 403 |
| 실패: 잘못된 상태값 | ✅ 400 (Y/N·날짜 형식·서류상태 값 검증) |
| 실패: 삭제된 매물 | ❌ **검증 로직이 없습니다.** 체크리스트 조회와 마찬가지로 매물 삭제 여부를 재확인하지 않아, 매물이 삭제된 뒤에도 항목 상태를 계속 변경할 수 있음 |

## 체크리스트 결과 확인 (`GET /checklists/{checklistId}/result`) — 요구사항 대비

| 요구사항 | 실제 구현 |
|---|---|
| 필수 항목 중 미확인 개수 계산 | ✅ `requiredMissingCount` |
| 주의 항목 수 계산 | ✅ `issueCount` (issueFound뿐 아니라 `userNote`가 있는 경우도 포함 — 아래 "추가 구현" 참고) |
| 등급/점수 대신 개수로만 표시 | ✅ |
| 시작 전이면 "체크리스트를 시작해보세요" 안내로 대체 | ✅ `message` 필드 |
| 실패: 존재하지 않는 체크리스트 | ✅ 404 |
| 실패: 확인한 항목 없음 | ❌ **이 케이스는 실패가 아니라 성공으로 처리됩니다.** 요구사항 문서 본문의 "시스템 처리" 설명("시작 전이면 안내로 대체")과는 일치하지만, "실패 사유" 목록에 있는 이 항목과는 실제로 모순됨 — 명세서 자체의 내부 불일치로 보이며, 실제 구현은 "시스템 처리" 쪽 설명을 따름 |
| 실패: 결과 계산 실패 | ❌ 계산 자체가 항상 성공하는 순수 함수라 이 실패 케이스는 발생하지 않음 |

## 비기능 요구사항 — 대조

| 항목 | 요구사항 | 실제 |
|---|---|---|
| 매물유형·거래유형에 맞는 항목으로 생성 | O | ❌ 위 참고 — 공통 템플릿 하나만 존재 |
| 동일 조건 매물엔 동일 버전 템플릿 적용 | O | ✅ (분기가 없어 사실상 전원 동일 버전이므로 자동 충족) |
| 템플릿 변경 이력을 버전으로 관리 | O | ⚠️ `version`이 정수 상수 하나로만 있고, 실제 이력 조회·자동 마이그레이션 체계는 없음 — Flyway 도입 전 임시 방식(seeder 방식)이라는 점은 이미 알려진 로드맵 |
| 하나의 유저-매물 조합엔 하나의 활성 체크리스트만 | O | ✅ DB 유니크 제약(`user_id`+`property_id`)으로 보장 |
| 체크리스트 항목은 반드시 체크리스트에 속함 | O | ✅ FK `nullable=false` |
| 삭제된 매물의 체크리스트는 수정 불가 | O | ❌ **생성 시점에만 검사하고, 조회/항목수정 시점엔 검사하지 않음** |
| 항목은 짧고 명확하게 | O | ✅ 시드 데이터 문구가 모두 한 문장 질문형 |
| 필수/일반 항목 구분 표시 | O | ✅ `importance` 필드 |
| `안전 점수` 대신 `확인 완료도`/`주의 항목 수` | O | ✅ |
| 상태 변경 즉시 반영 | O | ✅ (동기 처리, 별도 캐시/지연 없음) |
| 등기부등본 세부 항목에 안내 문구 제공 | O | ✅ `guideText` — 신탁등기/명의일치/소유권취득일 항목 모두 안내 문구 있음 |
| 동일 상태 변경 반복돼도 중복 저장 안 됨 | O | ✅ (필드 덮어쓰기 구조라 자연히 충족) |
| 저장 실패 시 완료로 표시 안 함 | O | ✅ (`@Transactional`로 실패 시 롤백) |
| 항목 변경 시 전체 체크리스트 재생성 안 함 | O | ✅ 항목 하나만 갱신 |
| 조회 시 매물 불필요 상세정보 미조회 | O | ✅ `Property`는 지연 로딩, ID만 사용 |

## 요구사항에 없던 추가 구현

- **`GET /checklists`(내 체크리스트 목록)** — 요구사항 명세서엔 없는 엔드포인트. 본인 매물 전체와 매물별 체크리스트 진행 상태(시작 전 포함)를 한 번에 보여주기 위해 별도로 추가됨
- **`userNote`(미흡 메모)** — CHECK 타입 항목에 "완료했지만 미흡함"을 메모와 함께 남기는 기능. 요구사항엔 없는 기능이며, `issueFound`뿐 아니라 `userNote`가 있어도 결과 계산의 "주의 항목"에 포함됨(`hasIssue() = issueFound || userNote != null`)

## 남은 이슈 / 확인 필요 총정리

1. 매물유형·거래유형별 문항 분기가 없음 — 템플릿이 버전 1 하나뿐이고 모든 매물에 공통 적용됨. 분기가 실제로 필요한 요구사항인지 확인 필요
2. 체크리스트 조회 시 카테고리·중요도 순 정렬 로직이 없음 — 생성 시 저장된 순서(`displayOrder`)만 그대로 반환되고, 카테고리 내 중요도 정렬은 반영 안 됨
3. 명의 일치 항목의 질문 방향이 요구사항과 반대(요구사항은 "불일치=Y", 실제는 "일치 여부"를 물어 "N"=불일치) — 동작은 같지만 문서와 헷갈릴 수 있음
4. 삭제된 매물에 연결된 체크리스트를 조회/수정하지 못하게 막는 로직이 생성 시점에만 있고, 조회·항목확인 시점엔 없음
5. 체크리스트 생성 실패 사유 중 "매물 정보 부족"/"지원하지 않는 매물 유형"이 실제로는 발생하지 않음(관련 검증 로직 없음)
6. 체크리스트 결과확인의 "확인한 항목 없음"/"결과 계산 실패" 실패 사유가 실제로는 발생하지 않음 — 요구사항 문서 자체의 "시스템 처리" 설명과 "실패 사유" 목록이 서로 모순되는데, 실제 구현은 전자(성공 + 안내 메시지)를 따름
7. 템플릿 버전 관리가 정수 상수 하나뿐이고 실제 이력 관리 체계는 없음 — Flyway 도입 전 임시 방식(`ChecklistTemplateSeeder`)이라는 점은 팀에서 이미 인지하고 있는 로드맵
