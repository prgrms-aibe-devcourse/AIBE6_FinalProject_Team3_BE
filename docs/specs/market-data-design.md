# 시세 데이터(market-data) 도메인 — 구현 현황 정리

## 배경 / 성격

`auth-design.md`, `user-design.md`, `property-design.md`와 같은 방식의 **회고성(retroactive) 문서**입니다. 다만 이 도메인은 다른 도메인들과 달리 **"요구사항 대비 얼마나 다르게 구현됐는지"를 비교할 대상 자체가 없습니다** — 코드베이스 전체를 검색해도 `market-data` 도메인은 **아직 구현되어 있지 않습니다.**

## 실제 구현 현황: 없음

- `MarketComparison`, `ComparableTransaction` 엔티티가 존재하지 않습니다.
- 국토교통부 실거래가 API를 호출하는 클라이언트가 존재하지 않습니다(`property` 도메인의 `KakaoAddressClient`처럼 외부 API 클라이언트 패키지가 따로 없음).
- 반경 확장(300m→600m), 면적 오차(±20%), 표본 최소기준(3건), 중앙값 계산 같은 정책 로직이 전혀 없습니다.
- 관련 `ErrorCode`(외부 API 장애/타임아웃/호출제한/응답형식오류, 판정불가 사유 등)도 정의되어 있지 않습니다.

**현재 유일하게 존재하는 흔적**은 `property` 도메인 안에 있는 자리표시자뿐입니다.

- `PropertyRegisterResponse.MarketComparisonResponse`, `PropertyDetailResponse.MarketComparisonResponse` — `status`, `referencePrice`, `differenceRate`, `sampleCount`, `referenceDate` 필드를 가진 record가 있지만, 실제 계산 로직 없이 `unavailable()` 정적 메서드로 **항상 `status="UNAVAILABLE"`, 나머지 필드는 전부 `null`인 값만 반환**합니다.
- 매물 등록(`POST /properties`)과 매물 상세조회(`GET /properties/{id}`) 응답에 이 고정값이 그대로 내려갑니다.
- 이 필드 구조 자체는 요구사항의 `MarketComparison` 엔티티(`referencePrice`, `differenceRate`, `sampleCount`, `referenceDate`, `status`)와 이름이 거의 일치해서, **응답 스키마는 미리 설계해뒀지만 실제 구현은 다음 단계로 미뤄둔 상태**로 보입니다. (`property-design.md`의 확인 필요 항목 #1, #2와 동일한 사안)

## 요구사항 대비 대조

이 도메인은 코드가 없으므로 항목별 비교표 대신, 요구사항에서 정의한 것과 실제로 준비된 것만 정리합니다.

| 요구사항 항목 | 실제 상태 |
|---|---|
| 매매시세 계산 정책(반경/면적오차/표본기준/계산식/조회기간) | ❌ 미구현 — 정책값을 담을 곳(설정/상수) 자체가 없음 |
| 국토부 API 호출(매물유형별 엔드포인트 분리) | ❌ 미구현 |
| 반경 확장(300m→600m) 로직 | ❌ 미구현 |
| 중앙값 계산 | ❌ 미구현 |
| 성공/판정불가/실패 3단계 응답 구조 | ❌ 미구현 — 현재는 사실상 "항상 UNAVAILABLE"이라는 네 번째 상태만 존재 |
| 데이터 기준일·조회시각·적용 반경 단계 기록 | ❌ 미구현 |
| 응답 스키마(대표시세/차이/차이율/표본수/기준일/status) | ⚠️ `property` 도메인 안에 필드 구조만 미리 만들어져 있고 값은 항상 비어있음 |

## 비기능 요구사항 — 대조

모두 미구현이며, 특히 아래 항목들은 지금 시점에도 이미 관련이 있어 확인이 필요합니다.

| 항목 | 상태 |
|---|---|
| 실거래가 API 실패가 매물 등록/조회 전체 실패로 이어지지 않아야 함 | ⚠️ 현재는 API 호출 자체가 없어 이 요구사항이 자동으로 지켜지는 셈이지만, 실제 연동이 들어가면 `property` 도메인의 `register`/`getProperty` 흐름에 실패 격리(에러가 나도 매물 등록/조회는 성공)를 별도로 설계해야 함 — `PropertyService`는 현재 이런 격리 로직을 고려하지 않은 채 짜여 있음 |
| 동일 매물 반복 조회 시 불필요한 외부 API 호출 감소(캐싱) | ❌ 캐시 계층 없음 |
| 주소/가격/거래유형 수정 시 기존 비교 결과 무효화 | ⚠️ `property` 수정(`PATCH /properties/{id}`)은 애초에 주소/거래유형 변경 자체를 막아뒀고(가격만 수정 가능), 가격이 바뀌어도 시세 비교 결과를 무효화하거나 재계산 트리거하는 로직이 없음 — `market-data`뿐 아니라 `property` 쪽에도 걸쳐있는 사안 |
| 실거래가 출처/기준일 사용자 안내 | ❌ 표시할 데이터 자체가 없음 |
| 반경 확장 여부 사용자 안내 | ❌ 미구현 |
| 판정불가 사유 안내 | ❌ 미구현 — 지금은 사유 구분 없이 무조건 `UNAVAILABLE` |

## 남은 이슈 / 확인 필요 총정리

1. **도메인 자체가 아직 구현되지 않았습니다.** 엔티티/외부 API 클라이언트/정책 로직/에러코드가 전부 없고, `property` 도메인에 응답 스키마 자리표시자만 있는 상태 — 담당자와 구현 일정 확인 필요
2. `property` 도메인의 가격/거래유형 수정 시 시세 비교 결과를 무효화하는 로직이 없음 — `market-data` 구현 시 `property` 쪽에도 연동 지점을 추가해야 함
3. API 실패 격리(외부 API 장애가 매물 등록/조회 자체를 막지 않아야 함) 설계가 아직 `property` 흐름에 반영되어 있지 않음 — 실제 연동 시 `PropertyService`의 예외 처리 전략을 함께 정해야 함
4. M1 기간 실측 재검증 예정이라고 명시된 정책값(반경 300/600m, 면적오차 ±20%, 표본기준 3건)을 하드코딩할지 설정값으로 뺄지 — 문서상 "버전을 기록"한다고 되어 있어 향후 변경 이력 관리 방식도 확인 필요
