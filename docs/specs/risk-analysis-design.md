# 위험도 분석(risk-analysis) 도메인 — 구현 현황 정리

## 배경 / 성격

다른 문서들과 같은 방식의 **회고성(retroactive) 문서**입니다. `market-data-design.md`와 마찬가지로 이 도메인도 **"요구사항 대비 비교"가 아니라 "미구현 현황" 문서**에 가깝습니다 — 코드베이스 전체를 검색해도 `risk-analysis` 도메인은 **아직 전혀 구현되어 있지 않습니다.**

## 실제 구현 현황: 없음

- `RiskSignal`, `DepositSafetyCheck` 엔티티가 존재하지 않습니다.
- 관련 컨트롤러/서비스/리포지토리가 전혀 없습니다.
- 관련 `ErrorCode`(계산 정책 오류, 데이터 조회 실패, 판정불가 사유 등)도 정의되어 있지 않습니다.
- `market-data-design.md`에서 이미 확인했듯, 이 도메인이 의존하는 **실거래가(매매시세) 데이터 자체도 아직 없습니다** — 즉 risk-analysis는 market-data에 대해 이중으로 막혀 있는 상태입니다(도메인 자체도 없고, 설령 만들어도 입력으로 쓸 시세 데이터가 없음).

## 다른 도메인에 남아있는 유일한 연계 흔적

risk-analysis 자체는 없지만, 다른 도메인들이 **미래의 연동 지점을 미리 준비해둔 흔적**은 몇 군데 있습니다.

- `property` 도메인의 매물 상세조회(`PropertyDetailResponse`)엔 위험 신호·안전성 정보를 담을 필드가 아예 없습니다(`property-design.md` 확인 필요 항목 #3과 동일 사안).
- `checklist` 도메인의 `ChecklistItemCode.OWNERSHIP_ACQUISITION_DATE`(소유권 취득일 문항)에 "risk-analysis 전세가율과 연계되는 보조 신호용"이라는 주석이 남아있습니다(`checklist-design.md` 참고). 다만 실제로 전세가율 값을 읽어와 조합 판단을 하는 코드는 없고, **주석으로만 연계 의도가 표시되어 있는 상태**입니다.
- `property`의 매물 삭제는 논리 삭제(soft delete, `PropertyStatus.DELETED`)라 삭제된 매물 데이터가 DB에 그대로 남아있습니다 — risk-analysis의 "짧은 주기 재등록 탐지" 신호를 만들 때 필요한 재료(삭제 이력)는 이미 준비돼 있는 셈입니다.
- `property`의 등록 시 중복 검사(`PROPERTY_DUPLICATE`)는 **"동일 사용자가 동일 주소·거래유형으로 재등록"**할 때만 걸리는 검사라, risk-analysis가 요구하는 **"서비스 전체에서 동일 주소·유사 조건으로 등록된 다른 매물(다른 사용자 포함 가능)을 탐지"**하는 신호와는 성격이 다릅니다. 두 메커니즘의 목적(전자는 중복 등록 차단, 후자는 다른 사용자의 매물까지 포함한 의심 신호 제공)이 다르므로, risk-analysis 구현 시 `property`의 기존 중복 검사를 재사용하기보다 별도 쿼리가 필요해 보입니다.

## 요구사항 대비 대조

이 도메인은 코드가 없으므로 항목별 비교표 대신, 요구사항에서 정의한 것과 실제로 준비된 것만 정리합니다.

| 요구사항 항목 | 실제 상태 |
|---|---|
| 가격 이상치 신호(시세 대비 10~20% 저렴) | ❌ 미구현 — 비교 대상인 대표 실거래가 자체가 없음(market-data 의존) |
| 동일 주소·유사 조건 중복매물 탐지 | ❌ 미구현 |
| 동일 계정 다수 등록 탐지 (🔶 논의중, 정책 플래그로 온/오프 요구) | ❌ 미구현 — 정책 플래그 구조 자체도 없음 |
| 짧은 주기 재등록 탐지 | ❌ 미구현 — 다만 위에서 언급한 대로 필요한 원재료(soft delete 이력)는 이미 있음 |
| 전세가율 계산(기본/선순위보증금 반영/근저당 채권최고액 반영) | ❌ 미구현 |
| 선순위보증금 검증(100~150% 강조 안내, 150% 초과 경고) | ❌ 미구현 |
| "최근 소유권 변경 + 높은 전세가율" 보조 신호 | ❌ 미구현 — `checklist` 쪽에 연계 의도 주석만 있음(위 참고) |
| 성공/판정불가/실패 3단계 응답 구조 | ❌ 미구현 |
| 정책 버전 기록 | ❌ 미구현 |
| 위험 신호 재계산(매물 수정 시 트리거) | ❌ 미구현 — `property` 수정(`PATCH /properties/{id}`)에도 이를 트리거하는 지점이 없음(`property-design.md`, `market-data-design.md`에서 이미 확인된 사안과 동일) |

## 비기능 요구사항 — 대조

모두 미구현이며, 특히 아래 항목들은 다른 도메인과 맞물려 있어 지금 시점에도 짚어둘 필요가 있습니다.

| 항목 | 상태 |
|---|---|
| 동일 입력·동일 정책 버전이면 동일 결과 보장 | ❌ 계산 로직 자체가 없어 N/A |
| 위험도 계산 실패가 매물 상세 조회 전체 실패로 이어지지 않음 | ⚠️ 현재는 계산 자체가 없어 자동으로 지켜지지만, 실제 구현 시 `PropertyService.getProperty()` 흐름에 실패 격리 로직을 새로 넣어야 함 — `market-data-design.md`에서 지적한 것과 동일한 패턴의 주의사항 |
| 실거래가 조회 실패와 위험도 계산 실패 구분 | ❌ 둘 다 미구현이라 구분할 대상이 없음 |
| 매물 정보/시세 변경 시에만 재계산(불필요한 재계산 방지) | ❌ 미구현 — 애초에 재계산을 트리거할 지점(`property` 수정 API)에도 아무 훅이 없음 |
| 동일계정 다수등록 탐지를 정책 플래그로 켜고 끌 수 있게 | ❌ 미구현 — 플래그 관리 체계(설정값/DB 등) 자체가 없음 |
| 서비스 대상 범위(전세+월세)와 안전성 체크 적용 범위(전세만) 화면 안내 구분 | 프론트엔드 영역 — 백엔드는 최소한 응답에 "월세는 판정불가" 상태를 내려줄 수 있어야 하는데 그 응답 자체가 없음 |

## 남은 이슈 / 확인 필요 총정리

1. **도메인 자체가 전혀 구현되지 않았습니다.** 엔티티/컨트롤러/서비스/에러코드가 전부 없음 — 담당자와 구현 일정 확인 필요
2. risk-analysis는 market-data(실거래가) 데이터에 의존하는데 **market-data 역시 미구현**이라, 두 도메인의 구현 순서를 어떻게 잡을지 확인 필요(risk-analysis를 먼저 설계하더라도 실제 동작은 market-data 완료 후에나 가능)
3. `checklist` 도메인에 남아있는 "전세가율 연계" 주석 외에는 실제 연동 코드가 없음 — 실제 구현 시 checklist의 소유권 취득일 값을 어떻게 읽어올지(체크리스트 조회 API 호출? 직접 쿼리?) 설계 필요
4. `property`의 기존 중복 등록 검사(동일 사용자 한정)와 risk-analysis가 요구하는 중복매물 탐지 신호(다른 사용자 포함 가능)는 서로 다른 메커니즘이라 재사용이 어려워 보임 — 별도 쿼리/로직 필요
5. "동일 계정 다수 등록 탐지"는 요구사항 문서 자체가 🔶 논의중이라고 표시한 항목 — Property 도메인이 "임대인이 아닌 일반 사용자가 검토용으로 등록"하는 구조라는 점 때문에 이 신호가 원래 의도(임대인/중개사 어뷰징 탐지)대로 작동하지 않을 수 있다는 점이 요구사항에도 명시돼 있음. 최종 탐지 기준과 온/오프 정책 플래그 설계는 팀 결정 대기
6. "선순위보증금을 매물 등록 시점에 받을지, 임장 체크리스트의 서류·행정 카테고리에서 받을지" 화면 흐름이 요구사항 자체에서도 미확정 — checklist 쪽 UX와 맞물린 결정이 필요
7. 위험 신호 재계산을 트리거할 지점(매물 수정 시)이 `property` 도메인에도 아직 없음 — risk-analysis뿐 아니라 market-data 쪽과도 함께 설계해야 하는 공통 훅
